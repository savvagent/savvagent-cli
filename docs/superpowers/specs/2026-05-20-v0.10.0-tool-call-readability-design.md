# v0.10.0 — Tool-call readability in the conversation log

## Motivation

Tool calls in the TUI's conversation log currently render as `name(<raw-JSON-truncated-at-80-chars>)`, dim-yellow. The arguments blob is a single dimmed line of compact JSON, often cut mid-token; results are raw text from the tool. The visual signal is "something happened" — the actual *what* requires squinting.

Two complementary fixes raise the readability of tool calls:

1. **Per-tool summaries** — for the six built-in tool names (`read_file`, `write_file`, `list_dir`, `glob`, `search`, `run`), render hand-tuned, human-readable lines (e.g. `read_file src/main.rs` and `1.2 KiB · 48 lines`) instead of dumping JSON.
2. **JSON syntax highlighting (with dim structural punctuation)** — for unknown tools, replace the dimmed-warning JSON blob with palette-aware spans: keys, string values, and number/bool/null literals get distinct colors; braces, brackets, commas, colons, and quotes are muted so structural noise recedes and data values pop.

Both fixes work on the same code path. Per-tool summaries are the bigger UX win for the common case; the JSON highlighter is the fallback that keeps unknown / future tools legible.

## Approach

Plugin-trait-based dispatch. The `Plugin` trait gains two summary methods; built-in plugins declare which tool names they own; the `PluginRegistry` indexes them and dispatches at render time. The TUI never names a tool directly.

This matches the project's existing "everything is a built-in plugin" pattern (the `crates/savvagent/src/plugin/builtin/` tree already contains `provider_anthropic`, `edit_file`, `route`, `save`, `splash`, and similar).

### 3. `savvagent` — three new built-in summary plugins

Mirroring the existing tool crates 1:1:

| Plugin module | Owned tool names |
|---|---|
| `plugin/builtin/tool_fs_summary/` | `read_file`, `write_file`, `list_dir`, `glob` |
| `plugin/builtin/tool_bash_summary/` | `run` |
| `plugin/builtin/tool_grep_summary/` | `search` |

All three are `PluginKind::Core` (not user-toggleable; they ship with built-in tools). Registered via `register_builtins()` in `crates/savvagent/src/plugin/mod.rs`.

Each summary plugin depends on its tool crate (`tool-fs`, `tool-bash`, `tool-grep`) and uses `serde_json::from_value::<*Input>(args.clone())` / `serde_json::from_str::<*Output>(result_text)` to recover the typed structs. If parsing fails, the plugin returns `None` and the TUI falls through to `json_spans`. (Parse failure should be impossible in practice — only happens on protocol-mismatch — but the design is robust to it.)

Rationale for typed parse over raw `Value` indexing: the tool crates own their input/output schemas. Compile-time-coupling the summary plugin to the schema means a refactor in `tool-fs` that renames `bytes` → `byte_count` breaks the build in the summary plugin instead of producing silently-blank summaries at runtime.

### 4. Per-tool rendering shapes (initial)

**Arguments:**

| Tool | Format |
|---|---|
| `read_file({path, max_bytes?})` | `read_file <path>` (+ ` (max <pretty>)` when `max_bytes` set) |
| `write_file({path, content, create_dirs?})` | `write_file <path> (<N> lines)` |
| `list_dir({path, recursive?})` | `list_dir <path>` (+ ` --recursive` when set) |
| `glob({pattern, root?})` | `glob <pattern>` (+ ` in <root>` when set) |
| `search({pattern, path?})` | `grep '<pattern>'` (+ ` in <path>` when set) |
| `run({command, cwd?, timeout_ms?})` | `bash $ <command-first-line>` (cap 60 chars; `…` if longer) |

`<path>` and `<pattern>` get the `success` palette role. Static prose (`read_file`, `--recursive`, etc.) gets `fg`. Optional suffix flags (`(max 1 MiB)`, `--recursive`) get `muted`.

**Results:**

| Tool | Format |
|---|---|
| `read_file → ReadFileOutput` | `<pretty(bytes)> · <line-count> lines` |
| `write_file → WriteFileOutput` | `wrote <pretty(bytes_written)>` |
| `list_dir → ListDirOutput` | `<entries.len()> entries` (+ ` (truncated)`) |
| `glob → GlobOutput` | `<matches.len()> matches` (+ ` (truncated)`) |
| `search → SearchOutput` | `<N> matches in <M> files` (exact shape pinned by `tool-grep::SearchOutput` at implementation time) |
| `run → RunOutput` | `exit <exit_code> in <elapsed_ms>ms` (+ ` (timed out)` if `timed_out`; + ` (stdout truncated)` / ` (stderr truncated)` flags) |

`pretty(N)` is a humanized byte count (`512 B`, `1.2 KiB`, `4.7 MiB`). Single helper in the highlighter utility module.

## Data flow

```
Provider streams ContentBlock::ToolUse { name, input }
        │
        ▼
App::on_provider_event pushes Entry::Tool { name, args: input.clone(), … }
        │
        ▼  (next frame)
render_log iterates entries
        │
        ▼
PluginRegistry::summarize_tool_call(name, &args, palette)
        │   ├── tool_summary_index["read_file"] → tool_fs_summary plugin
        │   └── plugin.summarize_tool_call returns Some(spans)  ────────► spans rendered
        │
        └── unknown tool: returns None
            │
            ▼
        json_spans(&args, palette) ──► fallback spans rendered

(symmetric for result_text when ToolResult arrives)
```

No new state, no new persistence, no new concurrency surface. Existing per-frame render lock is sufficient.

## Error handling

- **Tool not in index:** Fall through to `json_spans`. Logged once per session per unknown tool name at `debug!` level (no user-visible noise).
- **Result text doesn't parse as the expected typed Output:** Summary plugin returns `None`. TUI tries `serde_json::from_str::<Value>` to use the JSON highlighter; if even that fails (non-JSON result text), renders as muted plain text.
- **Plugin panics in `summarize_tool_call`:** Out of scope. The existing plugin runtime is in-process and doesn't catch panics; per-frame plugin panic is already an undefined-behavior surface and isn't changing here.

## YAGNI (deferred to later iterations)

- **Inline expand-on-keypress:** select a tool entry, press `Tab` or `Enter` to expand args and result to full pretty-printed form. Useful for debugging long arg blobs that get summarized. Defer until the new rendering lands and we see whether it's actually missed.
- **Write_file diff highlighting:** show a unified diff against current file contents for `write_file` calls. Real value, but requires reading the on-disk file at render time and a diff engine. Out of scope here.
- **Live `run` stdout streaming:** show command output as it streams rather than waiting for `ToolResult`. Requires protocol changes upstream of the TUI.
- **Making `tool-fs` / `tool-bash` / `tool-grep` themselves into plugins:** unrelated; tool ownership and tool rendering are separate concerns.
- **Syntax highlighting non-JSON result text:** highlight Rust code in `read_file` results, etc. Would need a syntax-highlighting crate; not worth the dependency for the current use case.

## Out-of-scope risks worth knowing about

- **Plugin overrideability:** if a third-party plugin registers a `ToolSummarySpec` for `"read_file"`, it shadows the built-in. This is intentional (consistent with slash-command override behavior) but should be called out in the third-party plugin docs.
- **Disable a built-in summary plugin:** the three new plugins are `PluginKind::Core` so they cannot be disabled via the plugin manager. If a user *needs* the raw JSON for debugging, the expand-on-keypress YAGNI item above is the answer.
